确认项目与环境

项目根目录是包含根级 package.json、docker-compose.yml 和 monopoly-zhenhuan_master-data.json 的目录。

进入项目根目录
cd "/path/to/monopoly-zhenhuan"
pwd
git status --short --branch
运行环境检查
docker --version
docker compose version

本机建议

macOS 或 Windows 使用 Docker Desktop。Windows 建议在 WSL2 内执行项目命令，并确保代码位于 Linux 文件系统中。

服务器建议

Ubuntu 22.04/24.04，至少 2 vCPU、4 GB 内存和 20 GB 可用磁盘。服务器区域尽量靠近主要玩家。

模式一

本机开发部署

适合开发、功能验证和单机演示。PostgreSQL、API 与 Web 全部由 Docker Compose 启动；宿主机不运行 npm 开发服务器。

准备环境文件

项目根目录
test -f .env || cp .env.example .env

如果 .env 已存在，该命令会保留原文件，不会覆盖密码和端口配置。

打开 .env，至少把 BOOTSTRAP_ADMIN_PASSWORD 改成 12 位以上强密码。不要提交 .env。

通过 Docker 启动完整系统

唯一启动方式
docker compose up -d
docker compose ps

首次启动会在容器内安装依赖、生成 Prisma Client、执行 migration、幂等 seed 并构建 API，耗时会比后续启动长。不要在宿主机启动 Web 或 API。

检查初始化日志

容器状态与日志
docker compose logs --tail=100 postgres api web

PostgreSQL 应为 healthy，API 日志应显示 migration 和 seed 成功。seed 会校验并幂等写入 26 块地产、五名人物和首个超级管理员，不会清空已有房间数据。

验证 Web 与 API

本机健康检查
curl --fail http://localhost:3000/
curl --fail http://localhost:4000/health

浏览器使用 http://localhost:3000，API 健康地址为 http://localhost:4000/health。

统一使用 localhost不要在一次登录流程里混用 localhost 与 127.0.0.1，否则 Cookie 与来源校验可能不一致。

第一次登录和创建账号

使用 .env 中的 BOOTSTRAP_ADMIN_USERNAME 和密码登录。进入超管后台后创建普通账号，并按需要授予“可创建房间”。系统没有游客注册入口。

5432 被占用时在 .env 中把 POSTGRES_PORT 改为 55432，并把宿主机工具使用的 DATABASE_URL 端口同步改为 55432，然后重新执行 docker compose up -d。API 容器仍通过内部网络访问 postgres:5432。

模式二 · 实体桌游推荐

可信局域网 HTTP 部署

玩家手机、平板和主持电脑处于同一可信 Wi-Fi 时使用。完整系统仍由 Docker Compose 启动，但必须在 .env 中写入精确的 CORS、Cookie 和 API 地址。

确认当前 Compose 与端口

先查看本项目容器，再确认 3000 和 4000 的监听者。若已是本项目 Compose，可直接在后续步骤重建；若是仍在执行的测试，等待测试结束，不另开端口。

本项目状态
docker compose ps
macOS / Linux
lsof -nP -iTCP:3000 -sTCP:LISTEN
lsof -nP -iTCP:4000 -sTCP:LISTEN

如有无关遗留进程，先确认工作目录和归属再处理。不要盲目使用 kill -9，也不要为测试另建端口。

确认电脑和玩家设备在同一 Wi-Fi

查看当前私网地址
# macOS 常见 Wi-Fi 网卡
ipconfig getifaddr en0

# Linux
hostname -I

有效示例包括 192.168.31.196、10.0.0.8。手机必须能访问这个地址，路由器不能开启客户端隔离或访客网络隔离。

写入精确局域网配置

以下示例假设主持电脑地址为 192.168.31.196。编辑 .env，保留 POSTGRES_BIND_ADDRESS=127.0.0.1，并设置：

.env
APP_BIND_ADDRESS=0.0.0.0
LAN_HTTP_ORIGIN=http://192.168.31.196:3000
NEXT_PUBLIC_API_URL=http://192.168.31.196:4000
NEXT_ALLOWED_DEV_ORIGINS=192.168.31.196

重建容器并实机验证

Docker Compose
docker compose up -d --force-recreate api web
docker compose ps

macOS 防火墙首次提示 Docker Desktop 接收入站连接时选择“允许”。至少用一台真实手机完成登录、进入房间、刷新页面和一次需要实时同步的操作。

主持电脑验证
curl --fail http://192.168.31.196:3000/
curl --fail http://192.168.31.196:4000/health
局域网模式只允许可信 Wi-Fi 不得在路由器或云防火墙中把 3000、4000、5432 映射到公网。HTTP 不加密，离开可信局域网就必须改用后面的公网 HTTPS 方案。

模式三 · 远程玩家

公网 HTTPS 生产部署

以下步骤以 Ubuntu 22.04/24.04、域名 game.example.com、项目目录 /opt/zhenhuan-monopoly 和密钥目录 /secure 为例。请把示例域名替换成你自己的域名。

当前版本必须知道的两点 当前系统使用账号 Session Cookie 和房间内独立银行能力，不使用旧版超管或银行令牌。公网 Nginx 没有把 /api/health 改写到 API 的 /health，健康检查要在 API 容器内部执行。

购买服务器并选择区域

选择靠近主要玩家的区域。建议 2 vCPU、4 GB 内存、20 GB 以上 SSD。一次玩家操作通常包含 HTTP 写入、Socket 通知和快照重拉，服务器跨洲会把延迟放大到数百毫秒。

配置 DNS

在域名服务商添加 A 记录：

DNS 示例

主机记录: game
记录值: <服务器公网 IPv4>
TTL: 300

等待解析后，在本机检查：

DNS 验证
dig +short game.example.com

如果服务器未配置 IPv6，不要添加 AAAA 记录。

登录服务器并设置防火墙

从本机连接服务器

申请 HTTPS 证书

确保 DNS 已生效、80 端口空闲，然后用 Certbot standalone 申请证书。

Let's Encrypt

证书路径
/etc/letsencrypt/live/game.example.com/fullchain.pem
/etc/letsencrypt/live/game.example.com/privkey.pem

生成两个独立的生产密码

分别执行下面两条命令。第一份输出用于数据库密码，第二份输出用于引导超级管理员密码；两份输出不能相同。生成值只包含十六进制字符，不会被 Compose 插值。

生成数据库密码
openssl rand -hex 24
生成引导管理员密码
openssl rand -hex 24

创建受保护的生产环境文件

创建目录与文件
sudo install -d -m 700 -o "$USER" -g "$(id -gn)" /secure
sudo install -d -m 700 -o "$USER" -g "$(id -gn)" /secure/backups
test -f /secure/zhenhuan.prod.env || sudo install -m 600 -o "$USER" -g "$(id -gn)" /dev/null /secure/zhenhuan.prod.env
nano /secure/zhenhuan.prod.env

/secure、环境文件和备份目录只归当前部署用户访问；后续 Docker Compose 与备份命令也必须使用同一用户执行。

填入以下内容。数据库密码在 POSTGRES_PASSWORD 与 DATABASE_URL 中必须完全相同；示例采用纯十六进制，可以避免 URL 编码问题。

/secure/zhenhuan.prod.env
POSTGRES_DB=zhenhuan
POSTGRES_USER=zhenhuan
POSTGRES_PASSWORD=<openssl-rand-hex-24 的输出>
DATABASE_URL=postgresql://zhenhuan:<同一个数据库密码>@postgres:5432/zhenhuan?schema=public

APP_ORIGIN=https://game.example.com
NEXT_PUBLIC_API_URL=https://game.example.com
APP_HOST=game.example.com

BOOTSTRAP_ADMIN_USERNAME=admin
BOOTSTRAP_ADMIN_PASSWORD=<至少 12 位的独立强密码>
BOOTSTRAP_ADMIN_DISPLAY_NAME=超级管理员
SUPER_ADMIN_USERNAMES=admin

TLS_CERT_PATH=/etc/letsencrypt/live/game.example.com/fullchain.pem
TLS_KEY_PATH=/etc/letsencrypt/live/game.example.com/privkey.pem
严格匹配来源APP_ORIGIN 与 NEXT_PUBLIC_API_URL 必须是同一个公网 HTTPS 地址，不带末尾斜杠；APP_HOST 只填写同一证书域名，不带协议、端口或路径。不要在生产文件中设置 LAN_HTTP_ORIGIN。

证书续期

本教程使用 Certbot standalone 验证，它续期时必须临时占用 80 端口，所以要先停止 Nginx。证书文件是宿主机上的符号链接，续期成功后强制重建 Nginx 容器，确保新证书重新挂载。整个过程通常只造成几十秒入口中断。

手工续期与恢复
cd /opt/zhenhuan-monopoly

# 临时释放 80/443；即使续期失败，也要执行最后的恢复命令
docker compose --env-file /secure/zhenhuan.prod.env -f docker-compose.prod.yml stop nginx
sudo certbot renew --standalone
docker compose --env-file /secure/zhenhuan.prod.env -f docker-compose.prod.yml up -d --force-recreate --no-deps nginx

# 检查外部实际提供的证书日期
echo | openssl s_client -connect game.example.com:443 -servername game.example.com 2>/dev/null \
  | openssl x509 -noout -dates -subject

Ubuntu 安装 Certbot 后通常自带 certbot.timer，但它不知道如何释放 Docker Nginx 的端口。为自动续期增加以下钩子；post 钩子会在尝试结束后恢复入口。

配置 Certbot 自动续期钩子
sudo tee /etc/letsencrypt/renewal-hooks/pre/zhenhuan-stop-nginx > /dev/null <<'SH'
#!/bin/sh
cd /opt/zhenhuan-monopoly
docker compose --env-file /secure/zhenhuan.prod.env -f docker-compose.prod.yml stop nginx
SH

sudo tee /etc/letsencrypt/renewal-hooks/post/zhenhuan-start-nginx > /dev/null <<'SH'
#!/bin/sh
cd /opt/zhenhuan-monopoly
docker compose --env-file /secure/zhenhuan.prod.env -f docker-compose.prod.yml up -d --force-recreate --no-deps nginx
SH

sudo chmod 700 \
  /etc/letsencrypt/renewal-hooks/pre/zhenhuan-stop-nginx \
  /etc/letsencrypt/renewal-hooks/post/zhenhuan-start-nginx
sudo systemctl enable --now certbot.timer
sudo certbot renew --dry-run
systemctl list-timers certbot.timer
先安排维护窗口renew --dry-run 也会运行钩子并短暂停止公网入口。执行后立刻访问首页，并用上方 OpenSSL 命令确认服务和证书正常。

先定位，再处理

常见故障排查

局域网昨天能开，今天地址打不开

最常见原因是电脑休眠、切换 Wi-Fi 或 DHCP 续租后 IP 改变。更新 .env 中的 LAN_HTTP_ORIGIN、NEXT_PUBLIC_API_URL 和 NEXT_ALLOWED_DEV_ORIGINS，执行 docker compose up -d --force-recreate api web，再把新地址发给玩家。旧书签不会自动更新。

3000 或 4000 端口已被占用
查找监听者
docker compose ps
lsof -nP -iTCP:3000 -sTCP:LISTEN
lsof -nP -iTCP:4000 -sTCP:LISTEN
lsof -a -p <PID> -d cwd -Fn

如果是本项目 Compose，复用现有 3000/4000；若测试正在运行则等待结束。只有确认是无关遗留进程后才终止，不要另开测试端口。

页面能打开，但登录后又回到登录页

检查是否把公网生产部署成了 HTTP、是否混用了 localhost 和 127.0.0.1，以及 APP_ORIGIN 是否与浏览器地址完全一致。生产 Cookie 是 Secure，公网必须 HTTPS。

API 返回 ORIGIN_NOT_ALLOWED 或浏览器显示 CORS 错误

局域网必须使用 LAN_HTTP_ORIGIN 配置的精确私网 IP 和 3000 端口，并确保 H5 使用同一 IP 的 4000 端口。生产的 APP_ORIGIN 只能是一个精确 HTTPS Origin，不得包含路径、尾斜杠或备用域名。

操作成功，但其他设备没有实时刷新

检查 Nginx 的 /socket.io/ 是否保留 Upgrade 头，API 是否只有一个副本。当前系统使用 Socket.IO 内存 Adapter，不支持多 API 副本。即使通知丢失，重新显示页面或重连会重新拉取 REST 快照。

公网 /api/health 返回 404

这是当前代理配置的已知差异，不代表业务 API 已损坏。使用容器内 http://127.0.0.1:4000/health；公网用首页 200 和 /api/auth/me 的预期 401 验证路由。

migrate 失败，API 一直没有启动

先查看 migrate 与 postgres 日志。核对 POSTGRES_PASSWORD 与 DATABASE_URL 密码一致；不要通过删除数据库卷来绕过 migration 错误。

Nginx 因证书文件无法启动

检查 TLS_CERT_PATH、TLS_KEY_PATH 是否是服务器上的绝对路径，文件是否存在，以及 Docker 守护进程是否能读取 Let's Encrypt 的符号链接目标。

Docker 构建被系统杀死或服务器失联

通常是内存不足。选择 4 GB 以上内存，构建时查看 free -h 与 dmesg。不要在生产高峰期同时构建多个 Next.js 镜像。

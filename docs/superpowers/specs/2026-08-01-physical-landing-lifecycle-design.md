# 实体落点持久化与生命周期

## 目标

让实体骰子模式中的落点成为服务端权威的“一次棋子移动上下文”。玩家刷新页面、断线重连、进入管理席位或在玩家端与银行端之间切换后，仍能恢复同一落点并继续处理关联事件；玩家声明下一次实体落点时，系统自然关闭上一次落点，不增加正常流程中的确认步骤。

## 核心规则

- 一次落点声明对应一次实体棋子移动，不对应某一个后续操作。
- 同一次移动产生的剧情结算、过路费、购买、建造、起点奖励及其他允许的事件共用同一个 `landingId`。
- 刷新、重连和工作台切换只重新读取服务端快照，不创建、关闭或作废落点。
- 每名玩家同时最多有一个可发起新操作的实体落点。
- 玩家声明下一次实体落点时，系统关闭上一个已经确认的实体落点，再创建新落点。
- 新声明替换尚未确认的声明时，视为更正：旧声明作废，新声明等待银行确认。
- 银行明确作废落点时，旧落点作废，并按现有规则取消其尚未完成的关联申请。
- 正常关闭不等于作废：关闭后不能再从旧落点发起新操作，但在关闭前已经提交并绑定该落点的申请仍可继续审批。

## 状态模型

`LandingEventStatus` 增加 `CLOSED`，形成以下状态：

```text
DECLARED --银行确认--> CONFIRMED --玩家声明下一落点--> CLOSED
    |                       |
    +--玩家更正-----------> INVALIDATED
                            |
                            +--银行作废---------------> INVALIDATED
```

- `DECLARED`：等待银行确认。玩家可提交新声明进行更正，不能执行依赖确认落点的操作。
- `CONFIRMED`：当前可用的实体落点。允许多个不同类型的合法后续事件共享该 `landingId`。
- `CLOSED`：正常结束的历史落点。禁止创建新的关联操作，但保留既有申请、账本和审计关系。
- `INVALIDATED`：错误或被银行撤销的落点。禁止继续使用，并取消仍待处理且依赖该落点的申请。

电子骰子模式继续以 `turnId` 和回合状态管理落点，不改用实体模式的“下一落点关闭上一落点”规则。

## 多事件处理

落点保持 `CONFIRMED`，直到下一次实体落点声明或银行作废。完成某一个事件不会自动关闭落点，因此玩家不需要为同一位置上的后续事件重复声明。

各事件继续独立限制重复执行：

- 剧情结算使用现有 `plotResolved` 表示是否完成。
- 过路费使用落点对应的结算记录和快照派生的 `tollSettled` 防止重复支付。
- 购买、建造和起点奖励通过绑定 `landingEventId` 的请求及既有业务约束限制重复提交或重复执行。
- 允许多条记录的其他剧情事件仍可共享同一个 `landingId`，由各事件自身规则决定次数。

“必要事项已结算”是界面提示，不是关闭条件。该提示只根据服务端快照派生：落点已经确认、剧情已经结算、应付过路费已经支付或被现有规则豁免，并且该落点已提交的申请没有等待玩家继续操作。购买、建造及其他可选行为不属于必须完成项。系统不根据完成第一个操作、经过固定时间或页面离开来关闭实体落点。

## 新落点与既有申请

创建实体落点时按旧落点状态处理：

1. 旧落点为 `DECLARED`：视为同一次移动的更正，将旧落点标记为 `INVALIDATED`；若存在依赖旧落点的异常待处理申请，按现有取消和解锁逻辑清理。
2. 旧落点为 `CONFIRMED`：视为下一次实体移动，将旧落点标记为 `CLOSED`，不取消已经绑定的待审批申请，再创建新的 `DECLARED` 落点。
3. 旧落点为 `CLOSED` 或 `INVALIDATED`：不再处理，直接创建新声明。

创建购买或建造等新申请时，只接受当前 `CONFIRMED` 落点。审批已经存在的申请时，可接受其落点为 `CONFIRMED` 或 `CLOSED`；若落点为 `INVALIDATED`，继续拒绝审批。这样关闭旧落点可以阻止迟到的新操作，同时不会破坏已经进入审批队列的操作。

## 快照与玩家端恢复

房间快照继续返回当前 `DECLARED` 和 `CONFIRMED` 落点；需要展示历史或审批关联时，可按请求关系返回必要的 `CLOSED` 落点信息。玩家端直接从快照中选择当前玩家最新的可用实体落点，不再要求落点 ID 同时存在于组件内存中的 `trustedLandings`。

页面恢复后的展示规则：

- `DECLARED`：显示“落点待银行确认”。
- `CONFIRMED` 且仍有未完成的必要事项：显示“本次落点”。
- `CONFIRMED` 且必要事项均已完成：弱化显示为“上次确认落点”，但仍允许规则许可的可选事件继续绑定。
- `CLOSED` 和 `INVALIDATED`：不作为当前落点展示，仅在历史、审批或审计记录中出现。

界面不得把实体落点描述为系统追踪的“当前位置”。实体棋子的位置仍以桌面现场为准。

## 双能力账号流程

同一账号兼任玩家和银行时，标准流程为：

1. 玩家端声明落点，服务端创建 `DECLARED` 记录。
2. 切换银行端，从银行快照看到同一记录并确认。
3. 切回玩家端，从玩家快照恢复为 `CONFIRMED` 的同一 `landingId`。
4. 玩家基于该落点完成一个或多个关联事件。
5. 玩家下一次声明落点时，服务端关闭旧落点并创建新声明。

工作台切换、管理席位和整页刷新均不参与上述状态迁移。

## 错误与并发处理

- 落点确认、作废和关联操作继续使用幂等键。正常关闭由幂等的新落点声明在同一事务内完成，不增加独立的关闭请求。
- 创建新实体落点时，在同一数据库事务中锁定房间或玩家的活动落点，关闭或作废旧记录后再创建新记录，保证每名玩家最多一个 `DECLARED` 或 `CONFIRMED` 实体落点。
- 银行确认与玩家新声明并发时，只允许一个有效结果：确认先完成则旧落点关闭并创建新声明；新声明先完成则旧声明作废，银行对旧 ID 的确认失败。
- 对 `CLOSED` 落点发起新的购买、建造、过路费或奖励操作返回明确的落点已过期错误。
- 对已经绑定 `CLOSED` 落点的待审批申请，银行仍可按原业务规则批准或拒绝。

## 非目标

- 不为实体骰子模式增加电子回合、掷骰记录或自动棋盘位置追踪。
- 不要求玩家每次完成落点后额外点击“结束本次落点”。
- 不使用 `sessionStorage`、`localStorage` 或禁止刷新作为业务状态依据。
- 不允许同一落点绕过现有剧情、过路费、购买、建造和奖励的次数限制。
- 不改变电子骰子模式的回合结束与落点失效规则。

## 测试

- 玩家声明实体落点后整页刷新，仍显示相同 `landingId` 和待确认状态。
- 双能力账号按玩家端声明、银行端确认、玩家端返回的流程，能恢复已确认落点并执行后续操作。
- 进入管理席位再返回玩家端，不清除落点。
- 同一确认落点可依次完成剧情结算及另一个合法关联事件，不要求重复声明。
- 完成第一个关联事件后刷新，其他合法事件仍能使用同一落点。
- 声明下一落点后，旧落点变为 `CLOSED`，不能创建新的关联操作。
- 旧落点关闭前已经提交的待审批申请不被取消，银行仍可审批。
- 更正未确认落点时，旧落点变为 `INVALIDATED`，银行不能再确认旧 ID。
- 银行作废确认落点时，关联待处理申请被取消并释放地产锁。
- 并发声明、确认和刷新不会产生两个活动实体落点。
- 电子骰子模式的回合落点、重新掷骰和结束回合测试保持通过。

## 方案取舍

仅将 `trustedLandings` 写入浏览器存储虽然改动小，但不能覆盖跨设备、缓存清理和服务端并发，不作为解决方案。直接从快照恢复最新确认落点可以解决刷新问题，但若没有独立的 `CLOSED` 与 `INVALIDATED` 语义，下一次移动可能误取消已经提交的申请。采用服务端生命周期需要数据库和校验逻辑调整，但能够同时满足刷新恢复、双端切换、多事件共用和旧落点自然结束。

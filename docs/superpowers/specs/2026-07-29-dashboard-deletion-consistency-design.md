# 数据看板删除一致性设计

## 目标

删除账号或房间后，超级管理员数据看板必须在下一次加载时只统计数据库中仍保留的数据。删除操作完成后，管理端既有的重新加载流程继续请求 `/api/admin/dashboard`，无需依赖前端缓存失效或人工刷新。

## 根因

数据看板的“人物选择”统计从 `SecurityLog` 中 `action = 'CHARACTER_SELECTED'` 的记录聚合。房间物理删除会删除结算、成员、资产和审计等房间数据，但未删除 `detailsJson.roomId` 指向该房间的 `SecurityLog`。因此已删除房间的人物选择日志仍存在并被看板计入。

管理端的 `mutateAndReload` 已在删除成功后重新读取账号、房间、日志和看板；问题不在前端状态刷新。

## 方案

在 `AccountRoomService.deleteRoom` 的现有单一事务内、删除 `Room` 前，删除 `SecurityLog` 中 `detailsJson.roomId` 等于目标房间 ID 的所有记录。该删除遵循现有物理删除能力开关，并使用 Prisma JSON path 条件精确限定目标房间。

账号删除保持现有行为：其所属或操作者安全日志已按账号 ID 清除。房间删除后的看板继续直接聚合保留记录，因此账号数、房间数、已结算对局、获胜次数、最近结束对局和人物选择次数都与数据库存储一致。

## 边界与错误处理

- 仅删除目标 `roomId` 关联的日志，保留其他房间和无关账号的日志。
- 日志删除与房间及其从属数据在同一事务内完成；任一步失败均回滚，避免看板与存储出现部分不一致。
- 不改动 `/api/admin/dashboard` 的响应结构、前端渲染或刷新时机。
- 幂等重放沿用现有删除契约，不重复执行删除。

## 测试

扩展现有 API 集成测试：创建两个带人物选择安全日志的房间，删除其中一个房间后请求 `/api/admin/dashboard`。断言已删除房间的选择记录不再出现或计数不再包含，另一个房间的选择记录仍存在；并断言目标房间的关联安全日志已被物理删除。

测试首先在未修复代码上失败，再以最小服务层改动使其通过。随后运行 API 对应测试、全量类型检查和受影响的前端管理流程回归测试。

## 自检

该方案将统计源中的孤儿记录与房间物理删除边界对齐，不通过前端补丁掩盖数据问题。修改范围限于现有删除事务和回归测试，且不会影响未删除房间的审计与统计。

# 资金流转 Toast 通知设计

## 目标

所有实际改变玩家余额的操作都产生轻量实时 Toast。玩家端只看到与自己有关的资金变化，银行端看到房间内全部资金流动。Toast 不替代账本，不要求用户交互，也不影响当前操作。

银行拒绝玩家提交的审批请求时，即使没有发生资金变化，也要向申请玩家发送独立的拒绝提醒。

## 范围

资金通知以已提交事务中的账本 effect 为唯一事实来源，覆盖：

- 初始资金；
- 玩家向玩家转帐；
- 玩家向银行支付；
- 银行向玩家付款、奖励或补贴；
- 银行扣款与剧情罚款；
- 买地、建房、抵押、赎回、出售建筑、出售地产和地产交易；
- 过路费；
- 技能造成的现金奖励；
- 事务撤销产生的反向资金变化；
- 后续通过统一账本事务新增的其他余额变化。

以下操作不产生资金 Toast：

- 仅创建待审批请求；
- 审批拒绝；
- 没有余额 effect 的操作；
- 同一幂等请求的重放。

审批拒绝虽然不产生资金 Toast，但会产生面向申请玩家的请求状态 Toast。拒绝提醒适用于所有由玩家发起并由银行拒绝的审批请求，不伪装成资金变动，也不写入账本。

## 方案选择

采用服务端在事务提交后生成结构化事件，并通过已授权的 Socket Session 通道精准推送。

不采用客户端余额差值推断，因为差值不能可靠表达交易对手、原因或多笔连续事务。不采用每次房间失效后增量拉取账本，因为这需要额外游标、补拉和去重协议，且实时提醒不需要承担断线恢复职责。

## 服务端设计

### 资金事件

资金事务在数据库成功提交后，根据已持久化的 `GameTransaction`、`LedgerEntry` 和玩家人物名生成结构化事件。事件至少包含：

- `eventId`：由事务 ID、受众角色和目标玩家 ID 组成的稳定去重标识；
- `roomId`；
- `audience`：`PLAYER` 或 `BANK`；
- `targetPlayerId`：玩家受众时必填；
- `transactionId`；
- `transactionType`；
- `amount`：对该受众使用正整数展示金额；
- `direction`：`IN` 或 `OUT`；
- `counterpartyKind`：`PLAYER` 或 `BANK`；
- `counterpartyName`：对手为玩家时使用人物名；
- `reason`：账本描述或规范化业务原因；
- `reversal`：是否为撤销产生的反向变化。

同一事务可生成多个受众事件。例如玩家甲向玩家乙支付时，甲收到转出事件，乙收到转入事件，银行收到一条全局资金事件。

只有首次实际执行事务的请求才派发事件。审批模式关闭时，转帐路由直接提交并派发；审批模式开启时，创建请求不派发，银行批准并提交事务后派发。幂等重放返回既有结果，但不再次派发。

### 拒绝事件

银行首次成功拒绝请求后，服务端向请求发起玩家的活动 Session 发送结构化 `request.rejected` 事件。事件包含稳定事件 ID、房间 ID、请求 ID、请求类型和银行填写的拒绝原因（如有）。幂等重放不重复发送。

默认玩家文案为“你的{请求名称}申请已被银行拒绝”；存在拒绝原因时追加“：{原因}”。银行端不接收这条 Socket 提醒，因为发起拒绝操作的银行端已有本地成功 Toast。

### 受众与隐私

服务端查询房间内有效成员及其 `activeSessionId`，通过现有 `session:<sessionId>` 通道发送：

- 参与资金 effect 的玩家只接收自己的玩家视角事件；
- 当前银行席位接收全部资金事件的银行视角事件；
- 请求发起玩家接收自己的拒绝事件；
- 其他玩家不接收事件，也无法从 Socket 负载看到无关交易。

兼任人物与银行的成员可以在同一 Session 收到两种受众事件。前端按当前工作台视图展示：玩家视图只消费 `PLAYER`，银行视图只消费 `BANK`。

Socket 资金与拒绝事件只用于在线实时提醒，不做离线补发。断线重连后余额和账本仍通过现有 REST 权威快照恢复。

## 文案规则

玩家视角优先使用以下句式：

- 玩家转入：`{人物名}向你转入 {金额} 两`；
- 玩家转出：`你向{人物名}支付 {金额} 两`；
- 银行发放：`银行向你发放{原因} {金额} 两`；
- 银行扣除：`银行扣除你 {金额} 两（{原因}）`；
- 向银行支付：`你向银行支付 {金额} 两（{原因}）`；
- 银行拒绝：`你的{请求名称}申请已被银行拒绝`，有原因时追加原因。

银行视角优先使用以下句式：

- 玩家向银行支付：`银行收到{人物名}支付 {金额} 两（{原因}）`；
- 银行向玩家支付：`银行向{人物名}支付 {金额} 两（{原因}）`；
- 玩家间流动：`{付款人物名}向{收款人物名}支付 {金额} 两（{原因}）`。

原因省略时不显示空括号。金额使用项目现有整数格式，不显示小数。撤销事件按反向后的真实方向组织文案，并在原因中标注“撤销”。

## 前端设计

工作台使用一个统一 Toast 队列承载现有操作成功提示、资金事件和拒绝事件，避免多个计时器互相覆盖。

- 队列按到达顺序逐条显示，同一时刻只显示一条；
- 每条完整显示 3 秒后自动移除，再展示下一条；
- 无关闭按钮，不获取焦点；
- Toast 容器使用 `pointer-events: none`，不阻挡页面点击和滚动；
- 使用 `role="status"` 和非打断式 live region；
- 按稳定 `eventId` 去重，防止 Socket 重复交付造成重复提醒；
- 离开房间时清空该房间尚未展示的通知，避免串房。

视觉沿用现有绿色成功 Toast 的纸张色、细边框和轻阴影。移动端固定在页头下方居中，宽度不超过视口并避开安全区；桌面端固定在内容区右上角。层级高于内容但低于需要用户决策的对话框，且不遮挡固定导航和主要操作按钮。

## 异常处理

- 资金事务回滚时不派发事件；
- 事件派发失败不回滚已提交资金事务，账本仍是最终事实；
- 无活动玩家 Session 时跳过该玩家的实时提醒，不补发历史 Toast；
- 没有银行在线时不影响资金事务，银行重新连接后通过账本查看历史；
- 缺失可选原因时使用通用句式，不能显示 `undefined` 或空括号；
- 事件负载无法通过前端校验时忽略该事件，不影响快照刷新。

## 测试与验收

服务端测试覆盖：

- 每种带账本 effect 的事务都能生成资金事件；
- 玩家转玩家生成付款玩家、收款玩家和银行三种正确受众；
- 玩家转银行、银行付款、奖励、扣款、地产资金、过路费、技能奖励和撤销的方向与文案数据正确；
- 审批关闭时立即派发，审批开启时只在批准入账后派发；
- 拒绝不产生资金事件，但向申请玩家发送拒绝事件；
- 幂等重放不重复派发资金事件或拒绝事件；
- 非相关玩家 Session 收不到交易负载；
- 双角色 Session 的事件具有明确受众角色。

前端测试覆盖：

- 玩家视图和银行视图只展示匹配受众的事件；
- 多条通知严格按序，每条显示 3 秒；
- 重复事件 ID 只显示一次；
- 请求拒绝文案及可选原因正确；
- 离开房间清空队列；
- Toast 不提供关闭交互且不阻挡点击。

浏览器验收覆盖手机与桌面视口，检查 Toast 的固定位置、连续队列、三秒消失、无内容重叠和操作区域可点击。

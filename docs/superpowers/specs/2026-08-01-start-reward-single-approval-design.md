# 起点奖励单次审批

## 目标

玩家端保留现有“精确停留起点”弹层和“声明停留起点”按钮。玩家点击一次后，系统直接向银行提交一笔 `START_REWARD` 款项审批；银行不再确认起点落点，玩家也不需要在银行确认后再次申请奖励。

银行待审批卡片继续使用普通款项审批样式，并在批准对勾下显示房间配置的起点奖励金额，例如 `+1,000`。银行批准后按现有资金结算逻辑向玩家发放奖励。

## 服务端状态流

`POST /api/rooms/:roomId/landings/start` 保留现有路由、玩家权限和请求参数，但将起点凭据与奖励申请作为一个原子操作处理：

1. 校验房间处于游戏中、玩家身份有效，并保留电子骰模式下当前回合和已掷骰校验。
2. 按现有规则替换同回合尚未使用的电子落点，或使该玩家旧的实体模式落点失效。
3. 创建 `START` 类型的 `LandingEvent`，直接标记为 `CONFIRMED`。它只作为奖励申请的内部校验和审计凭据，不代表银行确认过棋盘位置。
4. 在同一数据库事务中创建与该落点绑定的 `START_REWARD` `GameRequest`，状态为 `PENDING`，金额取 `Room.startReward`，并绑定当前电子回合（实体骰模式下不绑定回合）。
5. 只递增一次房间状态版本，并返回足以兼容玩家端现有落点信任逻辑的 `landingId`，同时允许前端识别奖励申请已经提交。

起点凭据从创建时就不是 `DECLARED`，因此不会进入银行端待确认落点集合。银行端只会收到 `GameRequest`。

## 幂等与重复申请

一次“声明停留起点”使用一个稳定的幂等键。相同请求重放必须返回首次创建的结果，不得再次创建落点或奖励申请。

同一有效起点凭据只能绑定一笔处于 `PENDING`、`APPROVED`、`EXECUTED` 或 `REVERSED` 状态的奖励申请。电子骰模式继续要求审批时该起点属于当前仍有效的回合；回合过期后银行批准应继续失败，避免补发失效回合的奖励。

银行拒绝奖励后，该次申请按现有拒绝规则结束，不自动创建新申请，也不改变其他地产落点状态。

## 玩家端

玩家看到的弹层布局、说明和“声明停留起点”按钮不变。点击成功后关闭弹层，并提示“起点 1,000 两申请已提交银行审批”（金额使用房间配置并按现有格式化函数展示）。

删除玩家端“等待银行确认起点落点”和“银行已确认后再次申请”的可达流程。兼容历史数据时，已存在的 `START + CONFIRMED` 落点仍可沿用现有奖励申请接口提交，避免正在进行的房间无法完成旧流程。

## 银行端

银行端统一待审批列表继续只把 `DECLARED` 落点作为落点待办。新创建的起点凭据为 `CONFIRMED`，不会渲染成“实体落点”卡片。

对应的 `START_REWARD` 请求使用普通请求卡片：标题为“起点奖励”，批准按钮使用现有对勾图标，并在图标下显示 `+<Room.startReward>`。拒绝、批准、实时刷新和到账通知继续走既有请求审批逻辑。

## 错误处理与兼容性

落点创建或奖励请求创建任一步骤失败时，整个事务回滚，不能留下需要人工处理的半成品落点。接口继续使用现有业务错误和幂等冲突处理方式。

不修改数据库结构，不新增银行接口，不改变地产落点的声明、剧情确认、购买、建造或过路费流程。

## 测试

- 服务集成测试：一次起点声明同时产生一个 `CONFIRMED` 起点凭据和一个金额正确的 `PENDING START_REWARD` 请求。
- 服务集成测试：银行快照不包含待确认起点落点，只包含起点奖励款项审批。
- 服务集成测试：同一幂等键重放不重复创建落点或奖励申请。
- 服务集成测试：银行批准一次后只发放一次配置金额，电子回合过期时仍拒绝批准。
- 前端测试：玩家点击“声明停留起点”只调用一次起点接口，成功文案直接表示已提交银行审批，不再要求第二次点击。
- 前端测试：银行 `START_REWARD` 卡片的对勾下显示 `+1,000`（或房间实际配置金额）。
- 回归测试：地产落点仍需银行确认剧情，其他普通请求审批行为不变。

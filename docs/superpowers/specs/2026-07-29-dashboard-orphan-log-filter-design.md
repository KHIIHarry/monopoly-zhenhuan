# 数据看板孤儿日志过滤设计

## 目标

数据看板的人物选择统计只计入仍存在的房间。已物理删除房间留下的历史安全日志不得继续显示在看板中。

## 现状与根因

房间删除事务现已删除 `detailsJson.roomId` 匹配目标房间的新安全日志。但部署该修复前已删除的房间留下了孤儿 `CHARACTER_SELECTED` 日志。实际数据库中这些日志的 `roomId` 已不在 `Room` 表中，而当前看板 SQL 仅按日志动作聚合，因而仍将其计数。

## 方案

调整 `/api/admin/dashboard` 的人物选择 SQL：使用 `INNER JOIN "Room"` 将 `SecurityLog.detailsJson.roomId` 与 `Room.id` 关联，并要求 `roomId` 非空。保留现有按人物 ID 和名称快照分组、排序及响应结构。

该查询边界即时过滤既有孤儿日志，无需删除历史数据；`deleteRoom` 中已有的同事务日志清理继续防止新孤儿日志产生。

## 测试

在管理 API 集成测试中创建一个现存房间和一个已删除房间对应的人物选择日志。看板结果只能包含现存房间的日志；在删除现存房间后，结果应为空。测试先在旧查询上失败，再修改查询使其通过。

## 自检

修改仅影响看板人物选择统计，未改变安全日志保存、账号统计、获胜统计、前端刷新或删除接口契约。SQL 以房间存在性为唯一过滤条件，符合物理删除后不显示其统计的业务期望。

# 房间垃圾桶与物理删除设计

## 目标

将超管后台现有的“归档房间”改为完整的房间删除生命周期：符合条件的房间先进入垃圾桶，保留 24 小时供超管恢复；到期后由 API 内置清理器自动物理删除，超管也可以在到期前立即物理删除。物理删除必须清除房间在 PostgreSQL 中的全部专属数据，不因房间已开局、已有账本、审计或结算而保留残余记录。

本功能只改变房间删除生命周期。账号删除、正常结束与强制结束、账本写入、结算生成及其他游戏规则保持现状。

## 生命周期与业务规则

### 删除前提

- `PLAYING` 房间禁止移入垃圾桶，接口返回稳定错误码 `ROOM_MUST_END_BEFORE_DELETE`。超管必须先通过现有“强制结束”生成结算并结束对局，或者等待对局正常结束。
- `LOBBY` 房间可以直接移入垃圾桶。
- `ENDED`、`FINISHED`、`CLOSED` 三种终态房间可以移入垃圾桶，不新增第二套状态枚举。
- 删除操作不再代替结束对局，不再取消进行中回合、请求或玩家控制权。`PLAYING` 的拒绝在任何写入前完成，失败时数据库保持不变。

### 进入垃圾桶

`Room` 新增三个可空字段：

- `deletedAt DateTime?`：进入垃圾桶的时间。
- `purgeAfter DateTime?`：计划物理删除时间，首次删除时固定为 `deletedAt + 24 小时`。
- `deletedByAccountId String?`：执行删除的超管账号 ID，关联 `Account`，删除账号时使用 `SetNull`，避免垃圾桶房间阻塞账号删除。

移入垃圾桶只写入以上字段并递增 `stateVersion`，不修改 `Room.status`。因此准备房间保留 `LOBBY`，已结束房间保留原终态和不可变结算。重复使用相同幂等键时重放首次结果；房间已经在垃圾桶内时，使用新幂等键再次删除也返回现有垃圾桶状态，不重置 24 小时期限。

### 恢复

恢复操作在事务中锁定房间行，清空 `deletedAt`、`purgeAfter` 和 `deletedByAccountId`，并递增 `stateVersion`，不修改原 `status`、结算或其他历史数据。

- `LOBBY` 房间恢复后仍是准备房间，可按原有流程继续配置和开局。
- 终态房间恢复后仍是只读历史房间。
- 不存在恢复为进行中对局的路径，不恢复进行中回合、待审批请求或玩家控制权。
- 已物理删除的房间无法恢复，返回明确的“房间已彻底删除或不存在”错误。

### 物理删除

物理删除是不可恢复的数据库事务。无论房间是否产生过游戏记录，都必须清除房间及其全部房间专属数据，包括：

- 房间成员、玩家及房间地产；
- 游戏请求、玩家间交易、资金事务和账本条目；
- 回合、实体落点事件、停轮记录和债务；
- 换角或换银行请求、游戏结果；
- 游戏结算和结算玩家明细；
- 房间审计日志；
- `detailsJson` 明确关联该房间的安全日志；
- `scope` 或请求载荷明确关联该房间的幂等记录；
- 最后的 `Room` 根记录。

人物、地产定义、共享账号、账号会话及其他房间数据不属于删除范围。当前项目没有房间专属文件存储，因此本次项目存储清理只涉及 PostgreSQL；未来若新增房间附件，必须将附件清理纳入同一生命周期并记录失败补偿，不能默认为已清理。

删除顺序必须遵循现有外键关系。服务层提供一个供手动删除和自动清理共同调用的物理删除事务函数，所有子表删除和根记录删除要么全部提交，要么全部回滚。

## 不可变数据规则

账本、审计、安全日志和结算数据在房间正常生命周期内继续保持不可更新、不可删除。用户对本功能的授权仅覆盖“房间已进入垃圾桶后的整房物理清理”，不是取消不可变规则。

现有 `allowPhysicalHistoryDelete()` 会写入事务级 `zhenhuan.physical_delete_txid`，但最新迁移 `202608010019_restore_room_history_immutability` 已撤掉 `LedgerEntry` 和 `AuditLog` 的物理删除例外；`GameSettlement` 与 `SettlementPlayer` 也从未开放该例外。新前向迁移必须统一定义 `LedgerEntry`、`AuditLog`、`SecurityLog`、`GameSettlement` 与 `SettlementPlayer` 的删除边界：仅当事务标记与当前事务 ID 匹配时放行 `DELETE`，普通事务的 `DELETE`、所有 `UPDATE` 和所有 `TRUNCATE` 仍然拒绝。授权必须使用事务局部设置，不能泄漏到连接池后续事务。

物理删除服务必须先确认房间处于垃圾桶，再启用事务级删除能力，并仅按已锁定的 `roomId` 删除。不得提供绕过垃圾桶直接物理删除活动房间的公共服务方法。

## API 设计

所有接口只允许当前有效的超级管理员会话访问，写接口要求 `Idempotency-Key`，并沿用现有管理写入与错误响应格式。

### 移入垃圾桶

```text
DELETE /api/admin/rooms/:id
```

成功返回房间 ID、`deletedAt`、`purgeAfter`、原状态和最新 `stateVersion`。`PLAYING` 返回 `ROOM_MUST_END_BEFORE_DELETE`；不存在返回现有房间不存在错误。

### 垃圾桶列表

```text
GET /api/admin/rooms/trash
```

返回所有 `deletedAt != null` 且尚未物理删除的房间，按 `purgeAfter` 从近到远排序。每项包含房间 ID、名称、房间码、原状态、删除时间、计划删除时间和删除操作者展示信息。前端基于服务器返回的绝对时间计算倒计时。

### 恢复

```text
POST /api/admin/rooms/:id/restore
```

事务锁定房间后恢复。成功返回恢复后的房间摘要和 `stateVersion`。相同幂等键重放结果；新键重复恢复已恢复房间时返回当前恢复状态，不产生第二次写入。

### 立即永久删除

```text
DELETE /api/admin/rooms/:id/permanent
```

只允许删除已在垃圾桶中的房间，调用共用物理删除事务。成功返回 `{ deleted: true, id }`。为了让网络重试可安全收敛，房间已经不存在时，无论使用原幂等键还是新幂等键都返回同样的成功结果，不重复执行删除。永久删除事务会清除该房间此前产生的所有幂等记录；删除完成后的确定性“不存在即成功”响应不依赖保留房间级幂等记录。

恢复和移入垃圾桶按现有管理操作约定写安全日志；这些日志在房间最终物理删除时与其他关联安全日志一并清除。永久删除成功只输出不落库的结构化运行日志，记录操作者或自动清理来源、房间 ID、房间名、动作和时间，不保留任何数据库房间记录。这样既能观测清理结果，也不违反“清除房间全部数据库数据”的要求。

## 可见性与访问隔离

进入垃圾桶后，房间立即从所有普通产品路径隔离：

- 普通房间列表、我的房间、历史列表、后台活跃/历史房间列表及统计均只查询 `deletedAt = null`。
- 通过房间码加入、通过现有成员身份重新进入、玩家端和银行端直接 URL 访问均视为房间不可用。
- 快照、游戏操作、配置、结算读取和其他房间 API 都必须拒绝垃圾桶房间。
- Socket 订阅在鉴权时拒绝垃圾桶房间；移入垃圾桶事务提交后通知当前连接离开该房间并刷新后台数据。
- WebSocket 只负责失效通知，客户端仍按既有原则重新拉取 HTTP 快照。

垃圾桶列表与恢复/永久删除接口是唯一可以访问垃圾桶房间的公共入口。所有相关查询应通过共享的“未删除房间”条件或专用查询方法实现，并用测试覆盖直接 API 路径，避免只在列表层隐藏。

## 自动清理器

清理器运行在 API 进程内：

- API 启动后立即扫描一次，补清理停机期间已经过期的房间。
- 此后每分钟扫描一次 `deletedAt IS NOT NULL AND purgeAfter <= now()` 的房间。
- 每轮最多处理固定数量的房间，避免持续占用数据库；每个房间使用独立事务，一个失败不阻塞同批其他房间。
- 每个删除事务在事务内使用 PostgreSQL `FOR UPDATE SKIP LOCKED` 选择并锁定一个到期房间，随后在释放锁前完成重检和物理删除。多 API 实例因此不会同时处理同一房间。
- 领取后在实际删除事务内重新检查 `deletedAt` 和 `purgeAfter`，避免扫描结果过期。
- 自动清理和管理端立即删除调用同一个物理删除实现。
- 清理器生命周期绑定 API 启停，关闭时清除定时器，不阻塞正常退出。

单房间清理失败时记录不落库的结构化错误并等待下一轮重试，不留下部分删除数据。永久删除成功同样输出结构化运行日志，以便从服务日志追踪操作者或自动清理来源；数据库不保留该房间的安全日志或其他墓碑记录。

## 并发与幂等

恢复、手动永久删除和自动清理都必须先对同一 `Room` 行加 `FOR UPDATE` 锁，并在锁内重检垃圾桶状态：

- 恢复先取得锁时，它清空删除字段并提交；随后清理器重检到房间未删除并跳过。
- 清理器或手动永久删除先取得锁时，它完成整房删除并提交；随后恢复得到“已彻底删除或不存在”。
- 两个清理器同时扫描时，`SKIP LOCKED` 确保只有一个实例领取目标。
- 手动永久删除与自动清理竞争时，只有一个事务执行实际删除，另一方按“已不存在即成功”的幂等语义收敛。

所有写接口继续使用前端生成的 `Idempotency-Key`。提交按钮进入加载态并禁用，防止重复点击；服务端幂等是最终保障。事务失败不能写入成功幂等结果，重试必须可以重新执行完整事务。

## 管理端界面

### 房间详情删除入口

现有“归档房间”改为“删除房间”。

- `PLAYING` 时按钮置灰且不可点击，说明“请先结束对局后删除”，不允许用户提交后才看到错误。
- `LOBBY` 或终态房间点击后显示危险确认弹窗，说明房间将进入垃圾桶、24 小时后自动永久删除、期间可恢复。
- 用户必须输入完整房间名称才能确认移入垃圾桶。
- 提交后立即显示加载状态；成功后关闭房间详情并刷新后台房间及垃圾桶数量。

### 垃圾桶入口

垃圾桶入口只在超管后台当前 `tab === "ROOMS"` 的房间功能页渲染。切换到账号、日志或其他功能页时不显示，并自动关闭已打开的垃圾桶面板。

入口固定在浏览器视口右下角，不可拖动，也不依附或挤压底部导航栏。使用 `lucide-react` 的 `Trash2` 图标，不使用 Emoji。按钮为简约圆形线性样式，触控区域至少 44px，目标尺寸 52px；显示待删除房间数量角标，并具备可访问名称和悬停提示。

桌面端点击后打开右侧抽屉，移动端点击后打开底部面板。面板不是嵌套卡片集合，列表项保持紧凑清晰。每个待删除房间显示：

- 房间名和房间码；
- 原房间状态；
- 移入垃圾桶时间；
- 按小时显示的剩余时间；
- 精确到分钟的自动删除日期与时间；
- “恢复”和“立即删除”操作。

倒计时小时数向上取整：例如剩余 23 小时 1 分显示“剩余 24 小时”；大于 0 且不足 1 小时显示“剩余不足 1 小时”；达到到期时间显示“等待自动删除”。前端每分钟基于 `purgeAfter` 重算，不自行延长或重写服务端期限。

“恢复”需要普通确认并在提交时禁用重复操作。“立即删除”使用危险二次确认，明确不可恢复，并要求输入完整房间名称；仅匹配后允许提交。操作成功后刷新垃圾桶、房间列表和统计。

## 错误处理与观测

- 所有服务错误使用稳定错误码；前端在原位置展示可理解的中文提示。
- `PLAYING` 删除失败、未在垃圾桶中永久删除、恢复已彻底删除房间、数据库事务失败分别有明确响应，不用模糊的“保存失败”替代。
- 清理器记录房间 ID、计划删除时间、尝试结果和错误，不记录密码、令牌或完整敏感请求。
- 任何删除事务失败都完整回滚；下一轮清理或用户重试可继续处理。
- 垃圾桶数量由服务端垃圾桶列表或专用计数派生，不把客户端缓存当成事实来源。

## 测试与验收

### 数据库与服务集成测试

- `PLAYING` 房间移入垃圾桶失败，房间、请求、回合、控制权和所有历史数据均不变。
- `LOBBY` 房间和每种现有终态房间都可以进入垃圾桶，状态不被改写，`purgeAfter` 固定为删除后 24 小时。
- 重复删除不延长到期时间，重复提交只执行一次实际写入。
- 垃圾桶房间从普通列表、历史列表、统计、房间码加入、直接 API 和 Socket 订阅中隔离。
- 24 小时内恢复会清空删除字段；`LOBBY` 仍为 `LOBBY`，终态与结算保持不变，且不恢复进行中回合、待审批或控制权。
- 到期前的扫描不删除房间；到期后的下一轮扫描完整删除；API 重启后的首次扫描补删停机期间过期的房间。
- 手动永久删除和自动清理删除完全相同的数据范围，保留共享账号、主数据和其他房间。
- 普通事务仍不能更新或删除账本、审计、安全日志、结算和结算玩家，也不能截断这些表；授权物理删除事务只能删除目标房间的数据。
- 多个清理器并发时同一房间只被处理一次。
- 恢复与清理竞态符合行锁顺序，不出现半删除、孤儿数据或已恢复房间被误删。
- 物理删除接口重复请求在房间已经不存在时仍成功，且不会误删其他数据。
- 物理删除中途任一步骤失败时整个事务回滚。

### 前端与端到端测试

- 垃圾桶按钮只在“房间”功能页显示，切换功能页后入口隐藏且面板关闭。
- 按钮固定在页面右下角、不可拖动、使用 `Trash2`，触控区域不小于 44px，数量角标正确。
- 桌面右侧抽屉和移动端底部面板均能完整查看与操作，不遮挡关键导航和提交控件。
- 列表按小时显示剩余时间，同时显示准确自动删除时间；每分钟更新且边界文案正确。
- `PLAYING` 房间的删除按钮在前端禁用；服务端仍独立拒绝绕过 UI 的请求。
- 移入垃圾桶、恢复和立即删除都有加载态及重复点击防护。
- 立即删除必须输入完整房间名，输入不匹配时不可提交。
- 恢复和删除成功后，普通列表、垃圾桶数量、统计及当前详情同步刷新。

### 最终验证

项目只通过 Docker 启动 Web 与 API，继续使用现有 `3000` 和 `4000` 端口，不通过 `npm` 启动服务，也不另开测试端口。质量检查执行：

```bash
npm run lint
npm run typecheck
npm run test
npm run build

```

## 文档影响

实施完成后更新 `README.md` 的超管房间删除说明，以及 `KNOWN_LIMITATIONS.md` 中与归档或删除保留有关的旧描述。API 文档明确四个端点、24 小时保留期、`PLAYING` 删除门槛和不可恢复的永久删除语义。

## 非目标

- 不提供玩家或银行自行删除房间的入口。
- 不允许删除进行中的对局，也不让“删除”隐式执行强制结束。
- 不恢复已物理删除的数据。
- 不为房间垃圾桶增加自定义保留时长、批量恢复或批量永久删除。
- 不引入独立队列、Redis、外部定时任务或新的服务端口。

## 自检结论

本设计将“历史不可变”解释为房间生命周期内不可删除或篡改，同时明确用户授权的整房物理清理事务可以删除该房间的历史数据。垃圾桶 UI 仅在超管“房间”页显示，固定在视口右下角，倒计时按小时展示并同时给出准确到期时间。恢复不复活对局运行态，物理删除以单事务和行锁保证完整性与并发安全。

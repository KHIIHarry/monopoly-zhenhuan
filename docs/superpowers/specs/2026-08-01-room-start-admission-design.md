# 房间开局清退与中途加入设计

日期：2026-08-01

## 目标

准备阶段允许任意数量账号先加入房间，再自行选择五个人物之一或取得唯一银行能力。银行确认开局时，只保留已经取得至少一种有效能力的成员，并清退既没有人物也不是银行的空身份成员。

开局后，房间是否接受新玩家由 `allowMidgameJoin` 决定；即使允许中途加入，也只有仍有空闲人物席位时才能加入。房间列表必须准确区分成员身份、游戏阶段与当前可加入性，实际加入失败时必须显示稳定、具体的拒绝原因。

## 已确认规则

- `LOBBY` 阶段加入账号不受人数和人物占用数限制。五个人物均已占用时，新成员仍可加入并在开局前申请人物或银行交换。
- 房间共有五个人物席位和一个银行能力。银行可由人物玩家兼任，也可由未选人物的独立账号担任。
- 开局清退条件严格为有效成员的 `characterId == null && isBank == false`。
- 纯银行成员、人物成员和人物兼任银行成员均保留。
- 开局仍要求 2 至 `playerLimit` 位有效人物玩家；纯银行不计入人物玩家数量。
- `PLAYING` 阶段只有 `allowMidgameJoin == true` 且有效人物数量小于 `playerLimit` 时才接受新玩家。
- “人物已满”只表示五个人物席位均已占用，不把银行另算作第六个人物名额。
- 管理页在准备阶段继续显示全部 `ACTIVE` 成员。未选人物成员仍出现在银行改派下拉框中，可先由管理员指定为银行，再由银行开局。

## 方案与边界

采用现有模型上的原子开局与实时可加入性计算，不新增持久化的“可加入”状态，不引入候补队列或席位预约表。

- `RoomMembership.status`、`leftAt`、`characterId`、`isBank` 和 `activeSessionId` 表达成员生命周期与能力。
- `Room.status`、`allowMidgameJoin`、`playerLimit` 和当前有效人物数量共同决定可加入性。
- 房间列表与实际加入接口必须调用同一套服务端规则，不能由前端单独猜测。
- 既有唯一约束继续负责同账号成员复用、人物唯一占用和银行唯一占用。
- 开局清退、交换申请终止、房间状态切换、首回合创建和版本递增必须在同一数据库事务内完成。

## 可加入性规则

服务端提供一个无副作用的统一判定，输入为房间阶段、`allowMidgameJoin`、`playerLimit` 和有效人物数量，输出为是否允许加入及稳定原因码。

| 房间阶段 | 条件 | 是否允许 | 原因码 |
| --- | --- | --- | --- |
| `LOBBY` | 任意成员数或人物占用数 | 是 | `null` |
| `PLAYING` | `allowMidgameJoin == false` | 否 | `MIDGAME_JOIN_DISABLED` |
| `PLAYING` | 允许中途加入，但有效人物数已达 `playerLimit` | 否 | `PLAYER_LIMIT` |
| `PLAYING` | 允许中途加入，且存在空闲人物 | 是 | `null` |
| `ENDED` / `FINISHED` / `CLOSED` | 任意 | 否 | `ROOM_FINISHED` |

当“关闭中途加入”和“人物已满”同时成立时，优先返回 `MIDGAME_JOIN_DISABLED`，因为配置本身已经禁止任何中途加入；人物数量变化也不会改变结果。

已是 `ACTIVE` 成员的账号进入自己的房间不重新执行加入判定。已被开局清退为 `LEFT` 的账号再次加入时，按普通非成员使用当前规则重新判定。

## 开局事务

`POST /api/rooms/:id/start` 继续由当前银行调用并使用现有幂等键。服务在房间行锁和 Serializable 事务内按以下顺序处理：

1. 验证调用账号仍持有该房间银行能力，并验证房间仍为 `LOBBY`。
2. 读取当前有效人物玩家，校验人数为 2 至 `playerLimit`，并校验成员人物与关联 `Player` 一致。发现人物身份数据漂移时中止开局，不把损坏数据当作普通空身份成员清退。
3. 找出所有 `status == ACTIVE && characterId == null && isBank == false` 的成员。
4. 将所有尚未完成的角色或银行交换申请改为 `CANCELLED`，设置 `resolvedAt`，拒绝原因为 `ROOM_STARTED`。交换仅允许在大厅处理，因此不论申请是否涉及被清退成员，开局后都不能继续悬挂。
5. 对每个待清退成员：如存在关联 `Player`，将其设为 `LEFT` 并清空人物；将成员设为 `LEFT`，清空能力与控制会话，写入同一个 `leftAt` 时间。
6. 将房间切换为 `PLAYING`，首次写入 `startedAt`，清理未开始的轮次字段；电子骰子模式使用开局前已验证的有效人物集合创建首个可行动回合。
7. 写入 `START_ROOM` 审计记录，并为每个被清退成员写入带 `ROOM_STARTED_WITHOUT_CAPABILITY` 原因的成员审计记录和安全日志。
8. 只递增一次房间 `stateVersion`，保存包括清退结果在内的幂等响应，然后提交事务。

任何一步失败都整体回滚。重放同一个幂等请求只返回既有结果，不再次清退成员、取消申请、创建回合或发送通知。

清退保留成员、玩家、账本及其他历史行，不做物理删除。被清退成员不再计入 `memberCount`、`mine`、游戏快照或结算玩家。

## 进行中原子加入

大厅继续沿用“先加入房间，再选择人物或银行”的两步流程。进行中房间改为“加入并选角”的单次原子操作，防止仅剩一个席位时多个账号都先获得空成员资格。

`POST /api/rooms/:id/join` 请求体新增可选 `characterId`：

- `LOBBY` 请求不要求 `characterId`，成功后进入现有席位页。
- `PLAYING` 请求必须携带 `characterId`。加入页先展示快照中的空闲人物，但该展示只用于交互，不能替代服务端最终校验。

进行中加入在房间行锁事务内完成：

1. 重新读取房间并按统一规则检查终局、`allowMidgameJoin` 和人物容量。
2. 验证房间密码及现有失败次数限制。
3. 验证 `characterId` 对应启用人物且尚未被有效成员占用。
4. 创建新成员，或复用该账号保留的 `LEFT` 成员行，并立即写入人物能力和当前控制会话。
5. 创建或重新激活其唯一 `Player`，分配未占用的棋子颜色和回合顺序。
6. 沿用现有中途加入经济规则：全新 `Player` 初始余额为 0，不发初始资金、不创建初始资金账本、不分配初始宫殿；保留的 `Player` 沿用现有重选人物语义，不重复发放任何初始资源。
7. 写入加入与人物选择安全日志，并只递增一次 `stateVersion`。

人物占用或最后一个席位的并发竞争由同一房间锁串行化。失败方收到 `ROLE_ALREADY_TAKEN` 或 `PLAYER_LIMIT`，事务不留下新的 `ACTIVE` 空身份成员。

## 房间列表契约与标签

房间摘要增加服务端计算字段：

- `canJoin: boolean`：当前账号不是有效成员时，现在是否允许发起加入。
- `joinBlockedReason: null | "MIDGAME_JOIN_DISABLED" | "PLAYER_LIMIT" | "ROOM_FINISHED"`。

`mine` 继续只表示当前账号在该房间存在 `ACTIVE` 成员。开局清退把成员改为 `LEFT` 后，下一次列表读取自然得到 `mine == false`，房间从“我参与的游戏”移动到“可加入房间”。私有房间对曾经加入过的账号继续保持既有可见性，不因清退从列表消失。

列表分组保持现有结构：

- “我参与的游戏”：`mine == true` 且房间未结束。
- “可加入房间”：`mine == false` 且房间未结束。该分组是未参与房间浏览区，其中可以包含当前不可加入的房间。
- “历史对局”：`mine == true` 且房间已结束。

徽标规则：

- 有效成员：`已加入` + `准备中` 或 `游戏中`。
- 非成员且 `canJoin == true`：`可加入` + `准备中` 或 `游戏中`。
- 非成员且 `canJoin == false`、房间未结束：`不可加入` + `游戏中`。
- 终局房间：只显示 `已结束`。

人物计数继续显示有效人物数，例如 `4/5 人物`；成员计数只统计 `ACTIVE` 成员，因此开局清退后会立即减少。

## 用户交互与实时反馈

- 非成员点击可加入房间时进入加入页。大厅保持现有密码加入流程；进行中房间同时显示当前空闲人物并要求先选人物。
- 非成员点击 `canJoin == false` 的房间时，不进入无效席位流程，直接用 `joinBlockedReason` 显示拒绝提示。
- 实际提交仍由后端重新判定。列表过期时，前端显示后端最新原因并刷新房间列表。
- 开局提交成功后，银行收到正常开局结果；其他有效人物或纯银行成员通过现有房间版本通知刷新到游戏状态。
- 被清退成员通过其会话通道收到成员资格移除事件，前端清理当前房间状态、返回房间列表，并提示“游戏已开始，你因未选择人物或银行身份已退出房间”。随后重新加载列表，房间按最新 `mine` 和 `canJoin` 归类。
- 通知只用于触发导航和重新获取权威 REST 数据，不把 Socket 负载作为成员或可加入性的最终状态。

## 错误处理

- `MIDGAME_JOIN_DISABLED`：`房间已开局，且不允许中途加入。`
- `PLAYER_LIMIT`：`房间人物已满，暂时无法加入。`
- `ROLE_ALREADY_TAKEN`：`所选人物刚刚已被其他玩家选择，请重新选择。`
- `CHARACTER_REQUIRED`：进行中加入未提交人物。
- `ROOM_FINISHED`：房间已经结束。
- `ROOM_PASSWORD_INVALID`：房间密码错误。
- `PLAYER_COUNT_OUT_OF_RANGE`：银行开局时有效人物少于 2 位或超过房间上限。

拒绝优先级为终局、关闭中途加入、人物已满、具体人物被占用、密码或其他输入错误。所有拒绝均由后端稳定错误码驱动前端文案；前端预判只改善体验，不改变授权结果。

## 代码落点

- `apps/api/src/account-room-service.ts`
  - 扩展统一加入判定并让列表摘要和加入事务共同使用。
  - 支持进行中加入携带人物并原子创建或复用成员与 `Player`。
  - 保持管理房间详情查询所有 `ACTIVE` 成员，不按人物筛选银行候选。
- `apps/api/src/prisma-game-service.ts`
  - 在现有开局幂等事务中加入空身份清退、交换申请终止、审计记录和提交后通知元数据。
- `apps/api/src/app.ts`
  - 扩展加入请求校验。
  - 开局提交后向被清退会话发送成员资格移除事件并撤销其房间订阅。
- `apps/web/app/components/app-router-client.tsx`
  - 使用 `canJoin` 和 `joinBlockedReason` 生成准确徽标和拒绝提示。
  - 为进行中加入增加必选人物控件。
  - 处理开局清退事件，返回列表并刷新数据。
- 现有 Prisma 模型足够表达该流程，不新增迁移。

## 验证

服务集成测试覆盖：

- 大厅中超过五个账号加入成功，五个人物全部占用后仍可加入空成员。
- 开局只清退无人物且非银行成员，保留人物成员、纯银行成员和兼任成员。
- 清退同时处理无 `Player` 成员和保留 `Player` 的空身份成员，且不物理删除历史。
- 开局取消全部待处理人物/银行交换，失败开局不取消、不清退、不创建回合。
- 开局重放及并发开局不重复写审计、清退或创建首回合。
- 进行中分别拒绝关闭中途加入、人物已满和终局房间，并验证错误优先级。
- 进行中原子加入成功后立即拥有人物与 `Player`；全新玩家为 0 余额且无初始资金账本或初始宫殿。
- 两个账号并发争抢最后席位或同一人物时只有一人成功，失败方不留下 `ACTIVE` 空成员。
- 被清退的 `LEFT` 成员在规则允许时复用原成员行加入，不产生重复成员。
- 管理房间详情在大厅继续返回未选人物的 `ACTIVE` 成员作为银行候选。

前端与浏览器测试覆盖：

- `已加入/可加入/不可加入` 与 `准备中/游戏中/已结束` 的全部有效组合。
- 被清退后房间从“我参与的游戏”移动到“可加入房间”，人数与人物数同步更新。
- `MIDGAME_JOIN_DISABLED` 与 `PLAYER_LIMIT` 显示不同拒绝提示。
- 进行中加入页要求选择空闲人物，并处理人物被并发占用后的刷新与重选。
- 当前停留在席位页的空身份成员在开局后立即返回列表并看到清退原因。
- 管理页银行下拉框在大厅包含未选人物成员，并可成功将其设为纯银行。
- 使用 Docker Compose 应用栈和 `PLAYWRIGHT_EXTERNAL_STACK=1` 运行相关 Playwright 流程，并执行相关 Vitest、类型检查、ESLint 与生产构建。

## 非目标

- 不引入候补队列、观战者、席位预约或自动候补补位。
- 不限制大厅成员总数，也不因大厅人物已满而拒绝加入。
- 不允许进行中新加入者只取得银行能力；银行改派继续由既有管理和角色交换规则负责。
- 不改变最少两位人物才能开局、初始资金、初始宫殿、结算或胜负规则。
- 不物理删除被清退成员及其历史数据。

# 实体事件与伙伴卡放回设计

## 目标

合并玩家实体事件面板中的冷宫与剧情停轮次数输入，在保留两种后端业务来源差异的前提下新增需要银行审批的实体伙伴卡放回流程。伙伴卡获得与放回均不再自动结算甄嬛技能资金，放回仅执行服务端固定的 500 两奖励。

## 方案比较

### 方案 A：沿用通用请求与审批事务（采用）

将 `RETURN_COMPANION_EVENT` 加入现有 `GameRequest` 类型白名单，玩家通过通用 `/requests` 接口提交 `{ playerId, type }`。服务端固定写入 `amount: 500`、`quantity: 1`，银行沿用现有批准、拒绝、幂等、房间锁和版本通知流程。

优点是审批状态、重复提交保护、事务边界和断线重连都复用已验证路径；无需数据库迁移，因为请求与事务类型均为字符串。缺点是必须在现有审批分支中为伙伴卡放回增加明确的数量、账本、审计和不可撤销处理。

### 方案 B：新增独立伙伴卡放回服务与路由

新增 `/events/companion-returned` 及独立批准方法，不经过通用请求动作。

接口表面更专用，但会复制请求状态机、幂等和审批逻辑，增加并发下出现不一致的风险，因此不采用。

### 方案 C：提交时直接结算

玩家点击后立即扣卡并加款，再让银行事后确认。

该方案违反审批前不得改变余额和数量的要求，因此不采用。

## 前端设计

实体事件面板只保留一个 `eventSkipCount`，默认字符串值为 `"1"`，冷宫与剧情停轮按钮共用其正整数校验。剧情说明只由 `PLOT_REST_EVENT` 使用：冷宫请求体不携带说明，剧情停轮在说明去首尾空格后为空时保持不可提交。

面板以两列网格显示四个操作：冷宫事件、剧情停轮、获得伙伴卡、放回伙伴卡。任一请求成功后关闭面板，并统一把次数重置为 `1`、剧情说明清空。全局房间写入锁继续保证同一时刻只有一个事件请求进入发送流程；连续事件必须重新打开面板。

点击放回伙伴卡时先关闭事件面板并打开独立确认框，避免两个模态框同时抢占焦点。确认框固定显示：

- 确认放回一张实体伙伴卡；
- 银行批准后获得 500 两；
- 该操作不关联落点，批准后不可撤销。

权威快照中的 `partnerCardCount` 为 0 时额外显示未记录实体卡警告，但确认按钮仍可用。确认请求体只包含 `playerId` 与 `type: "RETURN_COMPANION_EVENT"`，不包含金额、数量、落点、回合或骰子信息。

银行审批列表和批准确认框根据当前权威快照显示玩家、放回 1 张、奖励 500 两、当前是否为未记录实体卡放回，以及不可撤销提示。多笔待审批请求不在前端预占卡数。

## 服务端请求创建

`RETURN_COMPANION_EVENT` 复用 `createRequest()`：

- 不校验当前回合、骰子模式或实体落点；
- 不限制玩家当前 `partnerCardCount`，0 张时也可创建，多笔待审批也允许；
- 拒绝客户端传入金额、数量、地产、目标玩家、落点或原因；
- 服务端固定持久化 `amount: 500` 与 `quantity: 1`；
- 请求创建只写待审批请求和房间版本，不改变余额或伙伴卡数量。

请求创建的现有账号作用域幂等键和 canonical request hash 保持不变。同一玩家使用同一请求意图重复点击只得到同一笔请求，不同意图允许形成多笔待审批请求。

## 银行批准事务

银行批准时，在现有 serializable PostgreSQL 事务和房间行锁内重新读取玩家当前状态，而不使用提交时数量判定：

1. 原子声明待审批请求；
2. 读取批准时 `partnerCardCount` 和余额；
3. 若数量大于 0，数量减 1；若等于 0，保持 0；
4. 余额固定增加 500；
5. 创建不可撤销的 `RETURN_COMPANION_EVENT` 事务；
6. 创建一笔 `+500` 的不可删除账本；
7. 创建银行角色审计日志；
8. 请求标记为 `EXECUTED`；
9. 递增房间状态版本并提交幂等结果。

批准时数量为 0 的事务元数据和审计 `afterJson` 都写入 `untrackedPhysicalReturn: true`。有记录时写入 `false`，并同时保存批准前后数量、固定放回数量和奖励金额，便于审计。批准时判定可正确处理多笔待审批：例如只有 1 张记录时，第一笔批准扣至 0，第二笔随后按未记录实体卡放回执行并获得 500 两。

余额变化先产生标准 effect，伙伴卡数量更新使用玩家版本条件。事务、账本、审计、请求状态和幂等记录均位于同一外层事务；任何一步失败都会回滚已经执行的余额和数量变化。零数量永不执行减法，数据库现有 `0..3` 检查继续作为最后防线。

银行对同一请求重复批准时返回首次执行的事务结果，不新增余额、账本、审计或版本变化。事务的 `reversible` 固定为 `false`，不会出现在可撤销候选中。

## 甄嬛技能

删除 `COMPANION_EVENT` 批准分支中的甄嬛自动资金 effect，只保留伙伴卡数量增加。`RETURN_COMPANION_EVENT` 不读取人物技能配置，只执行固定 500 两。Master Data、人物技能数值以及前端展示文案保持原样，使线下玩家继续按实体规则自行记忆和裁定技能。

误批准放回不通过事务撤销处理。银行使用现有必填原因的余额人工修正抵消 500 两，伙伴卡记录需要恢复时提交并批准一次不再发放资金的“获得伙伴卡”事件。本次不新增独立伙伴卡人工修正入口。

## 冷宫与剧情停轮隔离

本次只合并前端字段：

- 冷宫仍提交 `COLD_PALACE_EVENT`，批准后创建 `COLD_PALACE` 来源，继续应用宜修减轮与补贴，并设置 `blocksTollCollection: true`；
- 剧情停轮仍提交 `PLOT_REST_EVENT`，批准后创建 `PLOT_REST` 来源，不应用宜修技能，并设置 `blocksTollCollection: false`；
- 两者继续累加玩家 `remainingSkipTurns`，不合并数据库记录或审批类型。

## 实时一致性

创建请求和批准请求继续在提交后调用现有 `notifyVersion()`。Socket.IO 只发送版本化失效通知；玩家和银行在收到通知、连接、重连、恢复网络、页面重新可见或手动刷新时重新拉取 REST 权威快照。无需新增事件负载或客户端增量合并逻辑。

## 错误处理

- 前端拒绝非正整数停轮次数；服务端继续二次校验。
- 剧情说明为空时前端不发送请求，服务端仍拒绝缺失说明的 `PLOT_REST_EVENT`。
- 放回请求携带客户端金额或落点等字段时服务端拒绝，防止绕过固定规则。
- 银行批准期间任何乐观锁、账本、审计或请求状态写入失败，整个事务回滚，请求保持待审批。
- 房间结束、身份失效、请求已处理和幂等键复用继续使用现有错误模型。

## 测试设计

### 服务与数据库集成测试

- 获得伙伴卡批准后数量增加但甄嬛余额不变，不产生 `SKILL_REWARD` 账本；
- 放回创建在审批前不改变余额或数量，且请求没有落点；
- 有记录批准后数量减 1、余额加 500，并写入一笔账本、事务和审计；
- 零记录仍能提交和批准，数量保持 0、余额加 500，事务元数据和审计含 `untrackedPhysicalReturn: true`；
- 多笔待审批依批准时状态依次执行；
- 相同请求重复批准只执行一次；
- 通过测试专用数据库触发器让审计写入失败，验证数量、余额、账本、事务、请求状态和幂等记录全部回滚；
- 第二个服务实例重新读取快照后看到最新卡数、余额、请求状态、账本和审计。

### API 测试

- 通用请求路由接受并原样转发 `RETURN_COMPANION_EVENT`；
- 服务端忽略不了客户端金额：携带金额或落点的放回请求被拒绝；
- 成功创建与批准继续把事务返回的 `stateVersion` 交给版本通知。

### 浏览器测试

- 面板只存在一个“停轮次数”输入，冷宫和剧情停轮提交不同类型与相同次数；
- 空剧情说明禁用剧情停轮，但不影响冷宫；
- 成功后面板关闭且重新打开时次数为 1、说明为空；
- 放回确认框固定显示三条说明，零卡时追加警告但仍允许确认；
- 前端放回请求不上传金额、数量或落点；
- 银行审批项和确认框显示固定数量、奖励、未记录状态及不可撤销提示；
- 快照刷新与 Socket 重连后显示批准后的权威状态。
